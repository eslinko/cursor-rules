# Процесс работы над таском (контракт + тесты + доки)

**Версия:** 1.4  
**Дата:** 2026-01-31  
**Применимость:** таски той же структуры (анализ → решения → архитектура → **план реализации** → фазы → тесты → документация → коммиты). Контекст: contracts/, scripts/, bot/ и т.д. Эталон: Task 1 ActivityRegistry (contracts/).

**Связанные документы:**  
- Стартовый промпт (пошаговое выполнение): `@.cursor/commands/run-task.md`  
- Анализ: `@.cursor/commands/run-analysis.md`  
- Фазы: `@.cursor/commands/run-phase.md`, `docs/methodology/multi-step-phase-execution.md`  
- Квалификация тестов: `@.cursor/rules/test-qualification.mdc`  
- Коммиты: `docs/methodology/git-commit-prompt.md`, `docs/methodology/git-commit.md`

---

## 1. Назначение

Один источник истины: **как мы работаем над таском** от постановки до пуша. Используется при планировании, при выполнении фаз и при напоминании «что на каком этапе делать». **Стартовый промпт** для пошагового выполнения с фидбеком оператора — **@.cursor/commands/run-task.md**.

Ключевая цель версии 1.4: исключить противоречивые реализации и «уход в fallback» при наличии явного списка `ACTIVE_TASK_PATH`.

---

## 2. Папка таска (working docs)

**Для каждого таска создаётся отдельная папка в `tasks/` по имени таска.** Путь зависит от контекста: `contracts/docs/analysis/tasks/task-<Name>/`, `scripts/docs/analysis/tasks/task-<name>/`, `bot/docs/analysis/tasks/task-<name>/` и т.д.

**Вся рабочая документация по таску кладётся в эту папку:**
- постановка и критерии (task-implement-*.md, task-*.md);
- решения (decision-points-*.md);
- архитектура решения (solution-architecture-*.md);
- **план реализации** (implementation-plan-*.md) — **обязателен перед любым кодом**;
- ретроспективы по фазам (phase*-retrospective*.md, phase*-process-retrospective.md);
- отчёты квалификации тестов, метрики (phase*-gas-metrics.md и т.п.);
- **верификация по критериям приёмки** (acceptance-verification-*.md) — **обязательна перед коммитами**;
- оценка приёмки (task*-acceptance-evaluation.md);
- CHANGELOG по таску (CHANGELOG-*.md);
- **итоговая ретроспектива таска** (retrospective-*-full.md).

Так проще **отслеживать**, что к какому таску относится, и при необходимости **удалить** или архивировать таск целиком (одна папка).

## 3. Этапы процесса

| № | Этап | Что делаем | Документ/команда |
|---|------|------------|-------------------|
| **0** | Стартовый резолв (обязательно) | Проверяем вход: если задан `ACTIVE_TASK_PATH` (строка или массив) — работаем **строго** по нему/по порядку массива; fallback по индексу запрещён. Если `ACTIVE_TASK_PATH` не задан — выбираем задачу из индекса по приоритету (`P0/P1` раньше `P2+`). | `run-task.md`, индекс bullrun, run-summary (фиксирует режим и источник). |
| **1** | Анализ и рамки | Читаем постановку таска и критерии приёмки; сверяем с тем, что уже есть в репо (эталон, напр. ProductRegistry); фиксируем **gap** (чего нет, что нужно сделать). | **@.cursor/commands/run-analysis.md** — только факты из кода, без предположений. Документ таска (task-implement-*.md, task-*.md). |
| **1.1** | Conflict-scan (обязательно) | До кода проверяем, нет ли в `Done/Done (Awaiting Commits)` задач с противоположным решением по тем же полям/контрактам. Если есть конфликт — останавливаем реализацию, создаём запись `superseded` и согласуем новое решение. | `rg` по tasks/instructions, acceptance notes, обновление индексов. |
| **2** | Решения до кода | Все спорные/важные решения выносим в документ (decision-points) **в папку таска**. Оператор явно выбирает варианты; фиксируем итог. Общие вещи (напр. роли экосистемы) — в канонический док в **перманентной зоне** docs, не только в папке таска. | decision-points-*.md (в папке таска); канонический док в корне docs. |
| **3** | Архитектура решения | Один документ (solution-architecture) **в папке таска**: что делаем, в каком виде, модель данных, роли, **фазы с шагами и артефактами**. План по фазам (0, 1, 2, …) с чёткими шагами и проверкой после каждой фазы. | solution-architecture-*.md в папке таска. |
| **4** | **План реализации** | **Обязательный этап перед любым кодом.** Один документ (implementation-plan-*.md) **в папке таска**: конкретизация по файлам и шагам — для каждой фазы/шага указать файл, место, действие, критерии приёмки. Источники: solution-architecture и decision-points. **Не переходить к этапу 5 (реализация по фазам), пока план реализации не создан и не зафиксирован.** | implementation-plan-*.md в папке таска. |
| **5** | Реализация по фазам | Идём по фазам **по плану реализации**. **Реализация по фазам включает все фазы из плана** (0, 1, 2, …). **Не считать этап 5 завершённым, пока не выполнена фаза с тестами**, если она есть в плане (напр. Phase 2 — добавление/изменение тестов). Каждую фазу выполняем по команде @.cursor/commands/run-phase.md (run-phase + документ с фазой N; ретроспективы по продукту и по процессу — в папку таска; маркеры [Phase N.X DONE]). Внутри каждого шага фазы: Planning (план изменений) → затем Implementation; **код только после плана по шагу.** После выполнения фазы с тестами — этап 7 (квалификация). | **@.cursor/commands/run-phase.md**, `docs/methodology/multi-step-phase-execution.md`. |
| **6** | Опциональные шаги | Для пунктов «при необходимости» / «опционально» в начале шага явно решаем: делаем или пропускаем и почему. Фиксируем в ретроспективе. | run-phase, multi-step-phase-execution (п. 1.1 «Опциональные шаги»). |
| **7** | Квалификация тестов и отчёт | **Любой созданный/изменённый набор тестов проверяем по @.cursor/rules/test-qualification.mdc** (честность, логика, P0/P1/P2). Итоговый отчёт квалификации **дорабатываем с учётом требований @.cursor/commands/run-phase.md** (ретроспектива по продукту, маркеры «Выполнено», сводная таблица). Отчёт — в папку таска. | **@.cursor/rules/test-qualification.mdc**, **@.cursor/commands/run-phase.md**. |
| **8** | **Верификация по критериям приёмки** | **Обязательная проверка перед коммитами.** Прогон тестов (подтверждение, что тесты зелёные). Сверка итогового кода и тестов с **критериями приёмки таска** (раздел AC/DoD в task-implement-*.md): по каждому пункту AC — соответствие кода и тестов; явные N/A с обоснованием. Документ **acceptance-verification-*.md** в папку таска (таблица: AC | уровень | формулировка | код/тесты | статус). **Не переходить к этапу 10 (коммиты), пока верификация не выполнена и не зафиксирована.** | Документ таска (AC/DoD); acceptance-verification-*.md в папке таска. |
| **8.1** | Верификация консистентности | Перед `Done`: подтвердить, что задача не противоречит активному решению по тем же полям (model/api/safety). Если противоречит — текущая или старая задача получает статус `Superseded` с явной ссылкой. | acceptance-verification-*.md + обновление bullrun/module index. |
| **9** | Документация | **Перманентная зона проекта:** `<контекст>/docs` (напр. contracts/docs, scripts/docs, bot/docs). Проверить по **типу контента**, что уже есть: архитектура, продукт, техчасть, API — возможно есть спецификация или шаблон. Создать или **интегрировать** документацию в нужное место (напр. описание контракта/скрипта/сервиса, API, роли, деплой). Канонические доки общего назначения — в корень соответствующего docs; при переносе из папки таска — зеркало (указатель) в папке таска. CHANGELOG по группам — в папку таска; в описании коммитов не перечислять файлы из папок тасков. | Существующие спецификации в `<контекст>/docs`; solution-architecture; CHANGELOG в папке таска. |
| **10** | Коммиты и push | **Методика @docs/methodology/git-commit-prompt.md и @docs/methodology/git-commit.md**: план коммита — **на согласование** с оператором; после одобрения — выполнение коммитов; **push только по явному разрешению** оператора. | **docs/methodology/git-commit-prompt.md**, **docs/methodology/git-commit.md**. |

## 4. Definition of Done таска

**Таск считается завершённым** только когда выполнены:
- этапы 0–9 (включая conflict-scan и верификацию по AC);
- этап 10 (коммиты — план согласован, коммиты созданы);
- итоговая ретроспектива (retrospective-*-full.md в папке таска).

При остановке до этапа 10 или без ретроспективы — **явно сообщить оператору**:
«Процесс не завершён. Осталось: [перечень]. Требуется согласование: [если есть]. Жду фидбек.»

---

## 5. Чекпоинт при остановке (обязательно перед завершением ответа)

Перед завершением ответа (после фазы, верификации и т.д.) **пройти чеклист и вывести блок**:
1. **(а) Что сделано** — какие этапы/фазы выполнены.
2. **(б) Что осталось** — этапы, которые ещё не выполнены (10 коммиты, ретроспектива и т.д.).
3. **(в) Что требует согласования** — план коммита, decision-points, опциональные шаги.
4. **(г) Жду фидбек** — явно запросить ответ («подходит» / «идём дальше» / «исправить»).
5. **(д) Режим запуска** — `ACTIVE_TASK_PATH` (строка/массив) или `fallback`, и почему.

Не завершать ответ, не выведя этот блок и не запросив фидбек (если таск не завершён полностью).

---

## 6. Итоговая ретроспектива

После завершения таска (до или после пуша): один документ **полная ретроспектива таска** — от постановки до пуша: что сделано, какие решения, что сработало / не сработало, уроки для следующих тасков. **Размещение: в папке таска** (напр. `contracts/docs/analysis/tasks/task-Activities-1/retrospective-task1-activity-registry-full.md`).

---

## 7. Краткая памятка для диалога

1. Сначала определить режим запуска: `ACTIVE_TASK_PATH` (строка/массив) или fallback; если задан `ACTIVE_TASK_PATH`, fallback запрещён.  
2. Папка таска в tasks/ по имени; вся рабочая документация — туда.  
3. Анализ (run-analysis) → gap, эталон.  
4. Обязательный conflict-scan по ключевым полям/контрактам до кода.  
5. Решения (decision-points) в папку таска; канонические доки — в перманентную зону docs.  
6. Solution-architecture в папку таска → фазы и шаги.  
7. **План реализации (implementation-plan-*.md) в папку таска — обязательно перед любым кодом; не скипать.**  
8. Каждую фазу — по **run-phase** (по плану реализации); **не пропускать фазу с тестами** (если есть в плане, напр. Phase 2); внутри шага: Planning → затем Implementation; ретроспективы в папку таска.  
9. Опциональное — явно «делаем» / «пропускаем».  
10. **Если в плане была фаза тестов** — выполнить её в рамках этапа 5; затем тесты — проверка по **test-qualification**; отчёт в папку таска.  
11. **Верификация по критериям приёмки** — прогон тестов, сверка кода и тестов с AC таска; acceptance-verification-*.md в папку таска; **не скипать перед коммитами**.  
12. Перед закрытием — консистентность: нет конфликта с актуальным каноном; если есть, ставим `Superseded` и отражаем в индексах.  
13. Документация — перманентная зона `<контекст>/docs`; по типу контента (архитектура, продукт, тех) создать или интегрировать; CHANGELOG в папку таска.  
14. Коммиты — **план на согласование**, затем коммиты; push — только по разрешению (**git-commit-prompt** + **git-commit**).  
15. Итоговая ретроспектива — **в папку таска**.  
16. **Чекпоинт при остановке** — перед завершением ответа вывести: что сделано | что осталось | что требует согласования | режим запуска | жду фидбек. Если таск не завершён (нет этапа 10 и/или ретроспективы) — явно: «Процесс не завершён. Осталось: …».
